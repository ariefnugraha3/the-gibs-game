## Dialogue presentation standard

Every spoken line shown in a dialogue box reveals character-by-character. The speaker label may appear immediately, but the body must start empty, type at the shared `CFG.campaign.dialogue.cps`, reach the exact full script, and remain complete for `holdSec` before advancing. This is the permanent standard for future dialogue UI; contextual lines queue rather than interrupting an active body. Narrative subtitles (`#cineCaption`) and compact HUD/status messages are not dialogue boxes and remain exempt.

`showStageRadioDialogue(speaker,text,typing,distorted=false)` also supports the Stage 4 Pilot signal-loss treatment. `distorted=true` toggles `.distorted` plus `dataset.distorted`, producing a reduced-motion-safe jitter/color split without changing the dialogue body; `hideStageRadioDialogue()` clears both typing and distortion state.

**The old `camera` is now a LOGIC PIVOT, not the renderer (top-down pivot 2026-07-11).** Its position = the player's eye-height point (feet + `eyeHCur`, same semantics as the FPS era) and its yaw = the AIM direction toward the cursor (set every frame by `updateTopdownAim` in input.js). Every gameplay system (robot targeting/claws, bullet/grenade/melee direction via `camera.getWorldDirection`, pickups, scene collision, radar, spawn points set by scenes) still reads `camera` and is UNCHANGED. Rendering is done by **`viewCam`** (renderer.js), a separate camera at fixed offset `CAM_OFF` (−70.7, 116, 70.7 — brought closer in steps 2026-07-11 [185/100 → 161/87 → 146/79 → 130/82]; then 130/82 → 116/100 LOWERED the angle a further ~15% while KEEPING the distance ~154 units [y down, z up] so only the pitch flattens, not the zoom: ~57.8° → ~49.2°; then **2026-07-16 the AZIMUTH rotated 45° from due-south to the SOUTHWEST** — the horizontal offset was split evenly x=−z [−70.7/+70.7], keeping horizontal distance ~100 & height 116 so pitch/zoom are unchanged, only the view direction turns) — Alien Shooter oblique angle. **`CAM_OFF` is the ACTIVE (mutable) azimuth, OVERRIDABLE PER-SCENE (2026-07-21): a scene may declare `camOffset {x,y,z}`; `applySceneCamOffset` (each frame in `followViewCam`) applies it — or restores `CAM_OFF_DEFAULT` for scenes without one — and recomputes the screen basis `SCREEN_UP`/`SCREEN_LEFT` IN PLACE (importers hold the same object refs, so WASD/radar/aim follow). The cursor raycast is unaffected (reads the real viewCam matrix), and the **radar was re-aligned to the SCREEN** (2026-07-16, see the HUD radar bullet — its projection frame is now `SCREEN_UP`, so radar-up = screen-up and the "N" marker points to true world-north up-and-to-the-left). `followViewCam()` tracks a **dead-zone focus point** `camFocus` (not the pivot directly): it only shifts when the pivot leaves a tolerance box of world half-extents `DEAD_X`/`DEAD_Z` (both **16** since 2026-07-16 — a SQUARE dead-zone per user request; `DEAD_X` was reduced from 46 to match `DEAD_Z`), so small movement doesn't move the camera (anti-dizzy, per user); **when the player STOPS moving the focus eases back to the pivot so the character re-centers** (2026-07-16 — `followViewCam(dt)` detects "stopped" via per-frame pivot displacement < `MOVE_EPS2`, then exponentially lerps `camFocus`→pivot at `RECENTER_RATE` 3/s; smooth, NOT a snap, to avoid dizziness); y follows without tolerance; jumps > 400 units (spawn/scene-change/restart) snap-recenter; **optional scene hook `camBounds()` (2026-07-17): a scene may return a world rect `{x0,x1,z0,z1,groundY}` the camera's visible ground footprint must stay inside — `followViewCam` clamps `camFocus` using `groundViewExtents(focusY, planeY)` (exported; projects the 4 screen corners onto the ground plane with pure trig from `CAM_OFF` + viewCam fov/aspect, no matrices) after the dead-zone/recenter branches, centering the axis if the rect is narrower than the footprint; null/absent hook = free camera (renderer.js now imports `activeScene` from sceneManager.js — import-free module, no cycle). ## Melee impact — blades & class-C claw (2026-07-27)

Both melee animations were already three-phase and reasonably posed; what they lacked was **the moment of contact**. A swing passed through the target and nothing acknowledged it. Three layers were added, shared by the player's blades and the robot's claw.

### Hit-stop — the single biggest change

`core/timeScale.js` is now **the** owner of the global time scale. It multiplies the two slowdown sources that exist — death slow-motion (`deathCine.js`) and melee **hit-stop** (`addHitStop(sec, scale)`) — and returns **exactly 1** when neither is active, so ordinary frames are untouched. `main.animate` reads `globalTimeScale()` and nothing else; `updateGame` decays the hit-stop with **dtReal**. A future slowdown becomes a factor inside that function, never a second multiplier in the render loop.

On contact, time drops to ~6% for ~75 ms (player) or ~12% for ~50 ms (robot — it attacks far more often, so a long freeze would feel like stutter), then eases out over the last 35% of the window so the release *snaps*. Because the scale is global, the swing, the target, the blood and the gibs all freeze together — which is what makes the brain read it as one collision with weight rather than a stutter.

### Player blades

- **Swings now ALTERNATE.** `meleeSide` (weapons.js) flips on every `tryMelee`; the avatar mirrors the whole choreography. (Since the 2026-07-29 knife rebuild what mirrors is the sweep direction of each blade AND which hand leads — see the section below; before that it was one sword's `yaw`/`roll`/`twist`.) Two swings in a row still never replay the identical clip; measured arcs are exact mirrors.
- **A follow-through phase** (k 0.52–0.74) replaced the flat recovery: the blade overshoots slightly past the cut and is hauled back by a damped bounce (`e^{-4.2t}·cos(13t)`), so the swing has mass instead of just stopping.
- **On connect:** hit-stop + `addCamShake(2.2)` + a spark puff and metal shards at the blade's contact point + a **blade flash** (`flashMeleeBlades` — the `steel` material is exclusive to the blades, and emissive is a uniform, so no recompile). The flash decays *outside* the melee branch, because a swing can end while the flash is still lit.

### Class-C robot claw

- **Legs finally participate.** Previously the attack was waist-up only while the legs kept walking. Now the rear leg loads during the wind-up and drives during the strike, the front leg plants and absorbs.
- **The eye telegraphs.** `rig.eyeMat.emissiveIntensity` ramps 1 → 3.2 through the wind-up and dims after the swipe — the tell is now readable at a distance, not just from the arm pose. The material is per-robot so one robot flaring doesn't light the others, and it eases back to *exactly* 1 (the walk pose never writes it, so a leftover value would stick forever).
- **A deeper lunge** (1.7 → 2.6 units) and a **damped post-impact shudder** in the settle phase — the frame's metal mass reads on landing.
- **On connect:** hit-stop + camera shake + sparks/shards at the contact point, alongside the existing red flash and hit-direction wedge.

Curve continuity matters here for the same reason as the roll: every phase hands off at matching values, and anything the living/walk pose doesn't write (`eyeMat.emissiveIntensity`, `bladeFlash`) must be driven back to its exact rest value rather than left where the animation stopped.

## Armor overlay — three readable tiers (rebuilt 2026-07-30, user request)

The old overlay was 20 flat slabs in three greys: a chest slab, two ellipsoid shoulder blobs, thigh/shin plates, a red stripe and a crest. The complaint was that it read as **flat and boring, and that you could barely tell the tiers apart** — which is fair, because from the top-down camera almost none of it changed the silhouette, and the only per-tier colour cue was a thin red stripe.

The rule that drove the rebuild: from this camera the player sees **shoulders, back, hips and the top of the head**. So each tier now changes exactly those.

- **I — Plate Carrier.** The chest is no longer one slab: a beveled top lip juts forward, a slanted belly plate sits under it, and two collarbone yokes angle in. Shoulders get thin two-slat caps instead of ellipsoid blobs, plus an amber ID tab. The silhouette stays as narrow as the unarmoured body — this tier reads as "plated", not "bulked".
- **II — Assault Rig.** Three flared slats per pauldron, each angled further out, so the shoulders get **visibly wider from above**; an armoured pack ridge with two canisters on the back; **tassets** (a segmented plate skirt) that widen the hips; greaves; helmet temple wings; and a sparing **red-white livery** on the chest (palette rule #3).
- **III — Exo Frame.** Outer plates shift to a **darker** steel, a gorget and collar wings rise around the neck, and a **spine power unit with four glowing amber cells** sits on the back — the one part that is unmistakable from directly above. Pauldrons gain a crown ridge with amber trim and a power node, and the chest gets an amber core, the helmet an amber visor and a standing crest. It is the only tier that glows at all, which is what finally makes tier III read as a different class of armour rather than "tier II plus a stripe".

**Two animation layers** (`updateArmorFx`): when the tier goes **up**, every active plate locks onto the body (scale 1.18 → 1 over `ARMOR_EQUIP_SEC` 0.5 s) while all plate paints flash amber — armour arriving now has a moment instead of popping in. And the tier-III power cells **pulse** slowly, then **flicker like failing power** once durability drops below `ARMOR_FAIL_FRAC` (30%), so the avatar itself tells you the armour is about to shatter. A tier going *down* (shatter) animates nothing — that already has its own gib/sound FX in `breakPlayerArmor`.

Cost discipline is unchanged: every armour material is built once at init (plain Phong, preload-warmed, one shared `aGlow` for all glowing parts), both animations only write **uniforms** (`emissive`, `emissiveIntensity`) and node scales, and the amber peak is capped at `EMISSIVE_MAX` 0.9. Both animations return to their exact rest values (scale 1, emissive 0) for the same reason as the blade flash and the robot's eye. Guarded by the `overlay armor …` asserts: cumulative counts, a strictly widening `span` per tier, a live pulse under the emissive cap, the low-durability flicker, and the equip animation settling back to exactly rest.

## Melee — dual combat knives (rebuilt 2026-07-29, user request)

The melee animation used to be a **sword** — a ~245° single-blade sweep from a pivot on the right shoulder. The user's objection was one of fiction, not of feel: *a modern soldier does not swing a sword.* So the character now fights with **two military-grade combat knives**, and the swing was re-choreographed around them.

**Nothing about the attack itself changed** — damage, range, duration (`MELEE_TIME`), stamina cost, cooldown, the ±70° front cone, the auto-target, and the 45%-of-swing hit moment all still live in `weapons.js` and were not touched. `playerAvatar.js` is purely visual, and even the phase thresholds (`A0` 0.18 / `A1` 0.52 / `A2` 0.74) were kept, precisely so the hit still lands while the blades are sweeping through the target.

**The rig.** Two pivots instead of one — `knifeR` at the right shoulder, `knifeL` at the left, both euler order `'YXZ'` as before. Each knife's meshes hang off a sub-group parked at the **grip point** (`KNIFE_GRIP`), which buys two things: the hand target is still one small manual euler rotation (`knifeHandTarget`), and the left knife can be flipped 180° into an **icepick reverse grip** without moving the point the palm attaches to. A knife is a pommel, a wrapped handle, a small crossguard, a flat blade with a fuller, and a flattened-cone clip point — about half the sword's length, which is why the swoosh fan was shortened and narrowed too (one per knife now, so the X is legible from the top-down camera).

**The choreography — a cross slash.** `knifeArc(u, s, down)` drives one blade: `u < 0` is the wind-up (snapped out to that hand's own side), `0…1` is the cut on a **quadratic ease-in** (so the blade crosses centre at ~70% of its own cut = the hit frame), `u > 1` is the damped follow-through that overshoots and bounces back. The lead hand starts at `A0` cutting **downward**, the other starts `KNIFE_LAG` (0.12) later cutting **upward** the opposite way — the stagger is what makes it read as two cuts forming an X rather than one wide arc. `meleeSide` mirrors both the sweep direction and *which hand leads*, so consecutive attacks still differ (the old alternation contract). Body dynamics — lunge, waist twist, crouch dip — are the sword's curves, unchanged: the attack kept its weight.

Guarded by the smoke asserts `DUA pisau belati…`, `SILANG X…`, `pisau kedua MENYUSUL…`, `koreografi BERCERMIN…` plus the untouched mechanics asserts (`MELEE_TIME`, front cone, auto-target, hit-stop, blade flash) — if the rebuild had changed damage, range, duration or area, those older asserts would have failed.

## Gunfire — cinematic recoil (rewritten 2026-07-28)

Firing used to be two things: a flash sprite at the muzzle, and `props.rotation.x = -gunRecoil × cameraKick × 6` — the barrel rose and fell **linearly** and nothing else on the body moved. Guns had no weight. The rewrite keeps every gameplay number untouched (fire rate, spread, heat, damage) and changes only what the shot *looks* like.

### One damped curve drives the whole body

`weapons.js` now runs a **shot clock** — `shotT` / `shotDur` / `shotKick` / `shotSide` (+ `recoilStack`) — instead of a single decaying scalar. `playerAvatar.fireCurve(u)` evaluates it:

- `u < 0.15` — smoothstep **snap** to 1 (about two frames: the punch),
- afterwards — `e^{−4.4v}·cos(2.3πv)`, a damped oscillator that **crosses zero**, so the muzzle dips *below* the aim line before settling. Same principle as the blade's follow-through and the robot's recoil bounce; a linear decay can never read as mass.

The signed value feeds **every** channel from one place, so no body part runs on its own timer:

| channel | what it does |
| --- | --- |
| `gunPitch` | barrel kicks up, then bounces through the line |
| `gunPush` | weapon travels back along the barrel axis — **both grip anchors move with it**, so the hands stay welded to the gun |
| `gunYaw` | muzzle is thrown sideways by `shotSide` (±1, random per shot) — no two shots are identical |
| `torso` / `twist` | upper body is shoved back and the shoulders wind away from the recoil |
| `headNod` | chin dips (via `lerpHeadPitch`, which also corrects the neck) |
| `bodyDip` / `kneeFlex` | the stance absorbs — body drops, knees fold |
| `shove` | heavy weapons physically push the avatar back a step (quarter strength for light ones) |

`recoilStack` is the **muzzle climb**: every shot adds `climbPerShot`, capped at 1, decaying at `climbDecayPerSec`. A long burst walks the barrel higher and higher and settles when the trigger is released — the reason sustained rifle fire now feels like it's fighting you. The whole overlay is written **last** in `updatePlayerAvatar` and is purely additive, so it rides on top of the idle/run/land pose without disturbing it, and it is suppressed entirely during a roll, a melee swing or the death sequence. Every channel is exactly 0 when no shot is live, so ordinary frames are byte-identical to before — except `lerpHeadPitch`, which is stateful and therefore gets driven back to exactly 0 by `fireHeadCur`.

### What leaves the barrel

- **Layered muzzle flash.** The single flat star sprite now expands as it fades (a blast, not a decal) and is joined by a **cone of gas** shooting forward along the barrel — the flat sprite alone read as a sticker from the top-down angle. Both live on `avatarGunTip`, so they are compiled during the avatar's warm-up render. The flash **PointLight is still the only one** — its intensity scales with the weapon and decays faster (`×42`).
- **Shell casings** (`effects.js`, fixed pool of 20, borrowed by `preload.warmupAll`): ejected right-and-back from the port, tumbling, arcing under their own gravity, **bouncing once** off the scene's ground height, then resting and fading. Deliberately oversized (~13 cm) — a real casing is invisible from this camera. The launcher ejects none.
- **Heavy-weapon blast** (`cameraKick ≥ heavyKick`, i.e. shotgun + launcher): a smoke ring at the muzzle plus **dust kicked off the floor** at the player's feet height, so the shot disturbs the world and not just the screen.
- **Barrel smoke** wisps from the muzzle once `gunHeat` passes `heatSmoke` — the existing spread-bloom heat finally has a visual.
- **Camera shake** per shot, `cameraKick × camShake` (≈0.3 units for the rifle, ≈0.8 for the shotgun) through the same `addCamShake` the explosions use.

**Toned down twice on 2026-07-28.** First pass cut the gun-side channels ~45% (`gunPitch` 7.5→4.2, `gunPush` 30→17, `gunYaw` 2.6→1.2, `twist` 2.6→1.3, `bodyDip` 14→8, `climbPitch` 4→2, `camShake` 26→17). The backward body push was raised in that same pass and the user rejected it outright — the whole avatar visibly lurching backwards on every shot looked absurd — so `torso` and `shove` were cut hard instead: **`torso` 3.4→1.6, `shove` 22→8, `shoveLightMul` 0.3**. The backward jolt is now a *nudge*, which is the point: **1.1° / 0.03 units for the rifle, 2.8° / 0.24 units for the shotgun** — enough to feel the shoulder absorb the shot, never enough to shift the character. If it ever needs re-tuning again, those two keys are the whole knob; do not scale them up to "sell" the recoil.

All amplitudes live in `CFG.weapons.recoil` and are multiplied by each weapon's existing `cameraKick`, so the pistol snaps, the rifle chatters, and the shotgun and launcher genuinely heave. Guarded by the `TEMBAK:` asserts in the smoke suite (curve shape including the negative overshoot, config-driven amplitude per channel, casing ejected/landed, heavy-only smoke, climb accumulation and decay, neutrality when idle, suppression during a roll).

## Run cycle (rewritten 2026-07-27)

The first gait was four lines: hip = a pure sine, knee = `max(0, ∓sin)`, a small torso bob. From the top-down camera it read as **a doll being slid along the floor** — the user's words were "masih terlihat sangat kaku". Three things were missing, and all three are what the eye actually uses to recognise a running human.

**1. The support leg was perfectly straight.** In the old curve the knee peaked exactly where the hip was most forward, so the leg carrying the body was rigid while the front leg curled up as it reached for the ground — backwards on both counts. `legCycle(th, ah, ak)` now builds the knee from two wrapped-gaussian bumps over the step angle (`sin(th)` = how far forward that leg is):

| `th` | moment | hip | knee |
| --- | --- | --- | --- |
| +π/2 | foot plants | max forward | ~0 — the leg reaches out |
| ≈ 2.80 | mid-stance | passing under | **0.6 rad — absorbing** |
| −π/2 | toe-off | max back | ~0.1 — straight push |
| ≈ −0.65 | mid-swing | under the body | **1.55 rad — heel to butt** |

The swing bump is deliberately **asymmetric** (narrow toward toe-off, wide toward the plant) so the knee stays straight while pushing off and folds deep while the foot is in the air.

**2. The body had no weight.** `bodyBob` runs at **2× the step frequency** with its minimum exactly at mid-stance — the same instant the absorption bump peaks, so the knee bends precisely as the weight drops. It is written to `avatarGroup.position.y` (pivot = the feet) and is always ≤ 0, so the avatar never floats above its standing height. The **head is counter-stabilised** by 55% of the bob (`headG.position.y`), the reflex that keeps a runner's gaze level. The whole body also **leans into the travel direction** (`rotateX`/`rotateZ` on the root, applied after the yaw), and the torso adds its own forward pitch. **Halved on 2026-07-28** (user: *"terlalu over condongnya"*) — root and torso together used to stack ~18° at full sprint, which read as charging head-first; they now stack ~10° (root `0.05+0.13·runK` → `0.03+0.07·runK`, torso `0.03+0.11·runK` → `0.02+0.05·runK`). Still clearly a run, but the head no longer outruns the feet. Visual-only constants, so they stay in code; the smoke assert is about *direction* (forward when advancing, backward when backpedalling), not magnitude, so it survives retunes like this.

**3. Both hands are on the weapon, so there is no arm swing to give.** The substitute is **shoulder-vs-pelvis counter-rotation**: `upperG.rotation.y = twistCur + torsoCounter`, where `torsoCounter` opposes the leg swing — and since the weapon is a child of `upperG`, that is what swings the rifle left and right. On top of it the weapon gets its own **inertia bounce**: it lags upward as the body drops, and the muzzle nods. The bounce goes through `props[key].position/rotation` — the same channel recoil already uses — so **`gunGrp` and `avatarGunTip` never move and the bullet spawn point stays calibrated**. The grip anchors receive the identical offset and pitch, so the palms stay welded to the grip and forend.

**Running while shooting** is the fourth state, and it is a damping term rather than a separate pose: `FIRE` (derived from `gunRecoil`) cuts the weapon bounce and the shoulder counter-swing by ~70%, so the legs keep sprinting while the rifle is **held still on the aim line** — which is exactly what separates "running" from "running and gunning".

All of it is visual only: bullet direction still comes from `camera` and the player's logical position is untouched. Amplitudes scale with `runK` (from real horizontal speed) and with `dirAmp` (strafing takes shorter steps); the cadence scales with speed too. `avatarGaitDebug()` exposes `{phase, runK, bob, counter, gunY, gunX, lean, headY, handRY}`, and the smoke suite asserts the properties that distinguish this curve from the old one: the knee never inverts, the stance leg flexes at the body's lowest point, the knee is extended (not curled) at the most-forward step, the bob is 2×/step and never positive, the hand moves with the weapon on every frame, cadence and lean follow speed and direction, everything decays to 0 on stop, and the bounce is damped while firing.

## Riding a vehicle — carried gait and the inertia lurch (2026-08-19, user request)

> *"buat agar ketika berbelok, major gibran tidak menampilkan animasi jalan. tampilkan animasi seperti terhempas. tau kan? aksi reaksi newton"*

**The walk cycle had to be switched off, not hidden.** The avatar's gait is derived from **pivot displacement** — how far the logic pivot moved this frame — so anything that moves the pivot without the player taking a step reads as walking. Stage 5's train hit this first (`setAvatarCarried`), and Stage 8's new free steering brought it back: every swerve slides the pivot sideways, so Major Gibran walked sideways in the roof hatch. Stage 8 now sets `setAvatarCarried(true)` for the whole ride, which pins the gait speed at zero while leaving the position updates alone.

**Then the swerve had to throw him.** `setAvatarVehicleLean(accel)` takes the vehicle's lateral acceleration, normalised to ±1, and rolls plus shifts the whole avatar in the **opposite** direction, on a lightly overshooting spring so the motion whips and settles instead of sliding into a static tilt.

Three details carry the physics:

- **It is fed acceleration, never velocity.** That is precisely the action-reaction the request asked for: holding a steady sideways speed lets the body come back upright, and it is *starting* and *stopping* the swerve that throws him — in opposite directions. A velocity-driven lean would look like a motorcycle banking into a corner, which is the wrong body language for someone standing in a hatch being shoved around.
- **The tilt is applied last in the frame**, on `avatarGroup.rotation.x`, so it rides on top of whatever pose the rig already chose — idle, firing recoil, the death collapse — rather than being overwritten by it. Euler `XYZ` puts Rx outermost, so the axis stays the world travel axis no matter which way he is aiming.
- **He physically shifts, not only tilts.** A pure rotation about the feet reads as posing; a small lateral displacement in the same direction sells being thrown.

**The amplitude is caged by the hatch, not by taste** (2026-08-19 follow-up: *"terhempasnya terlalu berlebihan, buat agar sedikit saja, agar major gibran masih tetap berada di area lubang di atas mobil"*). The feel constants came down to 0.15 rad of tilt and 0.9 units of shift (from 0.42 and 2.6) — this is the jolt of someone braced against a hatch rim, not someone being thrown off the vehicle. But the actual guarantee is `setAvatarVehicleLeanCage(halfWidth)`: the scene passes the roof hatch's **own** opening half-width, which `tacticalVehicle.js` derives from the leaf geometry and its slide rather than restating it as a literal, and the lateral shift is clamped to a fraction of that. So no later retune of the feel constants can put the gunner outside the hole he is standing in, and reshaping the hatch moves the limit with it. Measured peak across a full swerve-and-release cycle: **0.79 units of shift against a 3.29-unit half-opening, and 0.13 rad (7.5°) of tilt** — the values before this pass were 2.29 and 0.37 rad, which is 70% of the way out of the opening.

Manning a vehicle now also blocks the **AFK idle poses**. With the gait pinned at zero, `moving` is permanently false, so a gunner whose cursor sat still would previously have waved at the camera and eventually lain down on the roof of a moving vehicle.

Smoke drives all four properties in a live Stage 8 run: the run cycle stays at exactly zero while steering, the first frames of a swerve tilt him against the acceleration, holding the steer at constant speed returns him upright while the vehicle is still moving sideways, and releasing throws him back the other way. Reverting the carried flag reports `runK 0.62` — the walk cycle the report was about.

## Combat roll (dodge, rewritten 2026-07-27)

**Shift rolls, and it no longer looks like a mannequin spinning.** The 2026-07-12 version rotated the whole rig 360° on a smoothstep with a leg tuck — from the top-down camera that reads as *"just rotating 360°"* (user's words). The rewrite keeps the two things that were load-bearing and changes everything else.

**Kept:** the full **360°** (only a whole turn guarantees the body starts *and* ends upright facing the cursor with no pop) about the horizontal axis ⟂ the roll direction, orbiting the **waist-height pivot** `DODGE_PIV` 5.2 so the body turns about its centre of mass instead of scraping the floor.

**Changed — all driven off `dodgeProgress`, so everything follows `CFG.dodge.durationSec` automatically** (`dodgeCurves(p)` is the single source for the arm, torso and leg blocks):

| ~p | phase | what reads on screen |
| --- | --- | --- |
| 0–0.14 | **coil** | drops into a crouch, spine arches **back**, hands pull down and behind. **Zero rotation** — the anticipation beat the old one didn't have. |
| 0.14–0.30 | **launch** | legs snap, body leaves the ground, rotation bites |
| 0.30–0.68 | **air** | tightest tuck — knees to chest *and* **torso folded to the knees** — at peak rotation rate |
| 0.68–0.88 | **extend** | uncurls, legs reach for the floor, lead hand reaches down, the 360° completes |
| 0.88–1.0 | **plant** | foot contact, knees absorb, torso pitches forward |
| +0.22 s | **recover** | rises out of the crouch back to stance — runs *after* `dodgeActive` (and the i-frames) end |

The rotation uses **smootherstep over the window 0.10–0.88** rather than smoothstep over the whole span: it holds, explodes, then settles. The single biggest visual fix is the **torso curl** (`upperG.rotation.x` to ~1.0 rad at the apex) — without it the rig is rigid, which is exactly what "just a 360° spin" meant. Second is the **shoulder bank** (`DODGE_BANK` 0.62 rad about the roll axis, zero at both ends so the landing is level), which turns a straight-over-the-head flip into a diagonal shoulder roll. The bank side comes from the roll direction relative to the aim (sideways rolls go over the leading shoulder); for a pure forward/backward roll the side **alternates** each dodge so two in a row don't look identical. Legs are asymmetric (inner leg tucks tighter and extends first), the arms blend through four poses (`DA_COIL` → `DA_TUCK` → `DA_REACH` → `DA_BALANCE`), the head tucks its chin, and the **rifle is pulled across the chest** during the tuck (left at `GUN_OFF` it stabs through the floor when the body inverts).

**Curve continuity is the thing to preserve if you touch this.** Every phase's end value equals the next phase's start value, including the handoff into RECOVER — which is why `plant` is a monotonic ramp to 1 at p=1 rather than a sine bump (a bump returns to 0 and the recovery then starts from full weight, a visible 0.38 rad torso snap). RECOVER **crossfades** into the normal pose rather than adding on top, so the gait can take over immediately; it *assigns* `upperG.rotation.x` and the body height because the living pose chain only ever writes `upperG.rotation.y` — a leftover curl would otherwise stick forever.

**Travel profile** (`dodgeSpeedShape` in player.js): the old `(1 − p)` linear ease-out was fastest on the very first frame — it felt shoved, not launched, and didn't line up with any animation beat. Now it holds ≈0 for the first 8%, ramps hard to a peak ~1.55× the old one, then decays quadratically. **Total distance is preserved**: the shape is normalised so its area is 0.5, the area of the old `(1 − p)` curve, so `CFG.dodge.speed` keeps its tuned meaning. A side effect worth knowing: this also **fixed a frame-rate dependence** — the old discrete sum travelled 27.5 u at 30 fps vs 29.2 u at 144 fps, while the new one lands on 29.7 u at every rate. Worst-case single step is 6.1 u at 30 fps, far under the ~24 u a player would need to tunnel a 14-unit wall cell.

**Feedback:** a dust puff + whoosh (`sfxMeleeSwing`) on push-off, a dust puff + footstep + a small `addCamShake(1.4)` on landing — the old roll was silent and left no mark.

## Player death sequence (dramatized 2026-07-26)

**HP reaching 0 plays a directed ~2-second collapse, not a fall-over.** Before this, death was a single 0.6 s rotate-to-90° with the weapon simply hidden — flat and undramatic (user request: *"bikin jauh lebih dramatis"*). The work splits in three: `startPlayerDeath` (game.js) is only the GATE, `poseDeath` (playerAvatar.js) animates the body, and **`core/deathCine.js` is the director** holding the sequence's REAL-time clock.

**Body — four phases** (durations are visual constants in playerAvatar.js, exposed via `avatarDeathTiming()`; every phase's end values equal the next phase's start values, so there are no pops — a per-frame jump check is part of the smoke suite's intent):

| phase | ~game-sec | what happens |
| --- | --- | --- |
| `impact` | 0.13 | the body is STRUCK: spine arches BACKWARD *against* the fall direction (`fall` −0.30), both arms are thrown up and back (`DH_THROWN`), head snaps back, heels lift, torso spins by `deathSpin` (random ±). The arch **holds at its peak** at phase end (`sin(u·π/2)`, not `sin(u·π)`) so it doesn't flick back to neutral. The **weapon is released here**. |
| `buckle` | 0.34 | knees SURRENDER: hips drop to `BUCKLE_Y` (−2.0), knees fold asymmetrically (one gives first), torso folds forward, head drops, one hand reaches for the floor (`DH_BRACE`). `fall` passes from −0.30 through upright to +0.42 on an `e²` curve — it hangs, then tips. |
| `fall` | 0.26 | GRAVITY: `fall` ease-INs to 90° **+0.14 overshoot**, the root rises from −2.0 to `LIE_Y` (1.25) so the corpse rests **ON** the floor instead of half-sunk (the old animation left it embedded), and the body starts rolling onto one shoulder (`roll`). Phase end = the GROUND IMPACT cue. |
| `settle` → `still` | 0.52 | damped rebound: `fall`, height, knees and limbs oscillate with an `e^{−5.5u}` envelope (≥2 direction reversals), the head lolls to the side, one last chest heave, then absolute stillness at exactly 90°. |

The root pivot is still the FEET, so "hips drop" can only be expressed by lowering the root — which also sinks the boots. `BUCKLE_Y` is deliberately kept as shallow as the AFK crouch (−1.7); the *read* of buckling comes from the knee/torso folding, not from depth. Waist twist and head turn left over from the living pose are **whipped** to zero across the impact instead of being zeroed in one frame.

**The weapon is genuinely thrown, not hidden.** `releaseGun` re-parents the EXISTING `gunGrp` to the scene (`sc.add` — same meshes, same materials, so **no allocation and no shader recompile**), keeps the held prop visible, hides the rest, and gives it a ballistic arc + tumble (`gravity` from CFG, one weak bounce, then it comes to rest on its side). It lands slightly AFTER the body. `resetAvatarDeath` re-parents it to `upperG` and restores the calibrated `GUN_OFF`, so the invariant that `avatarGunTip` never moves is preserved. Dying mid-melee (no prop in hand) throws nothing.

**Director (`core/deathCine.js`)** — ticked from `updateGame` with **dtReal** (unscaled), so slow motion never stretches the wait for the GAME OVER screen:

- **Slow motion** is the only global time scale: `deathTimeScale()` ramps 1 → `CFG.player.death.slowMoScale` over 0.12 s, holds `slowMoHoldSec`, then eases back over 0.8 s. `main.animate` computes `dt = dtReal × deathTimeScale()`; the world AND the collapsing body share it, so the whole thing slows together. It returns exactly 1 when idle — normal frames are byte-identical to before.
- **Death cam**: pushed into the renderer via `setDeathCam(zoomMul, orbitRad, tiltRad)` — renderer.js does NOT import deathCine (same "inject the value" pattern as `setQualityLightRef`, keeping renderer CFG-free). `followViewCam` rotates `CAM_OFF`'s azimuth by `orbit`, scales the whole offset by `zoom` (closer to the corpse, max `CFG.player.death.camZoom`), and applies a **dutch tilt** with `viewCam.rotateZ` after `lookAt`. All three are neutral at 1/0/0 = the old math exactly.
- **Screen**: `#deathFx` (a radial blood-red vignette, z 8 — above `#damage`, below `#gameOver`) gets a per-frame opacity of `max(punch, close)` — a fast red PUNCH decaying at τ=0.10 s, then a slow closing-in to 0.92. No CSS transition, because JS owns the curve. The canvas itself is graded toward monochrome with a CSS `filter` (`setDeathGrade`: saturate 1→0.14, brightness →0.66) — the canvas only, so the GAME OVER text stays crisp. Letterbox bars slide in via `setCineBars`, but **only if a cutscene isn't already using them** (`barsOwned`).
- **Audio**: `duckMusic(k)` (sfx.js) fades the battle track over 1.6 s so the music SINKS instead of being cut. It writes the element's `.volume` directly without touching the Settings slider; `playTrack`/`stopMusic` restore `musicVol`, so no duck ever leaks into the next run. A pitched-down (`playbackRate` 0.4) `sfxExplode` gives the "world drops out" whump at the moment of death.
- **FX cues follow the BODY's phase, not a timestamp**: the director polls `avatarDeathPhase()` and fires `groundImpact()` on the transition into `settle` — dust puffs under the corpse, a wide low blood spray, pool decals at torso and head, `addCamShake(CFG.player.death.camShake)`, a pitched-down thud + a gear "crack". A wider pool spreads 1.2 s later.

**Two-step teardown, deliberately:** `gameOver()` calls `endDeathCine()`, which stops the clock, releases slow motion and retracts the letterbox but **freezes the framing** (camera still close/tilted, world still desaturated, vignette still closed) — the corpse stays composed behind the panel. Resetting the camera here would make it visibly snap back through the only-80%-opaque GAME OVER overlay. `resetGame()` calls `resetDeathCine()`, which restores everything. `endDeathCine` is safe on the WIN path (it was never active).

Tuning lives in `CFG.player.death` (`slowMoScale`, `slowMoHoldSec`, `camZoom`, `camShake`) plus the existing `CFG.player.deathDelaySec` (4 s — the sequence needs ~2.1 s, leaving a held beat before the screen). Pose amplitudes and phase lengths stay in code per the project's "visual-only values stay in code" rule.
