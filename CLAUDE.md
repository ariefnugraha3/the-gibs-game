# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- **Serve:** `python -m http.server 8000` (then open http://localhost:8000) — an HTTP server is MANDATORY; `file://` breaks ES modules + the config `fetch`. Internet required for the Three.js r128 CDN scripts.
- **Test:** `node tools/smoke.mjs` — headless smoke suite (zero deps, stubbed THREE/DOM driving the real `src/` modules), currently 626 asserts. Sections are `// === NAME ===` comments wrapping a `{ … }` scope block; each assert is `T(name, ok)` ([smoke.mjs:202](tools/smoke.mjs#L202)). The `[postfx] … CDN tidak termuat` line it prints is expected (no network in Node), not a failure. There is **no per-test filter** — it's a flat sequential script, so run the whole file (comment out sections to isolate one). The `localStorage` stub is a real in-memory Map, so save/checkpoint is testable. Coverage list at the end of MODULES.md.
- **Lint:** `node --check src/<file>.js` — per touched file (`"type": "module"` makes this work).
- **Mandatory per gameplay change:** add/adjust smoke asserts → `node tools/smoke.mjs` until green → `node --check` every touched file → sync CLAUDE.md + MODULES.md.
  - Keep asserts **CONFIG-DRIVEN** (read `CFG`, never hardcode tuned numbers). The user hand-tunes `config/gameplay.json` between sessions; a test failing right after a pure config retune almost always means the test hardcoded a number.
  - A missing stub method (fakeEl/THREE) is a harness gap, not a game bug — extend the stub.

## Overview

Browser **TOP-DOWN SHOOTER** (Alien Shooter-style; **pivoted from FPS on 2026-07-11** — see the "camera is a logic pivot" rule below): "Gibran vs Robot 3D", Three.js r128.

**Controls: WASD = screen-axis movement, mouse = virtual aim cursor (bullets follow it), LMB = shoot/use, RMB = move-to-cursor-point (WASD cancels), 1/2/3 = the three weapon slots, Q cycles weapons, 4 = use a medkit instantly, F melee, Shift dodge/evade (brief-invincible **combat roll** — animation rewritten 2026-07-27, see docs/presentation.md). Crouch, jump, ADS, sprint (replaced by the dodge), R/reload (magazine system removed) and the thrown grenade (replaced by the Grenade Launcher weapon) do not exist** — all removed in the 2026-07-11 pivot. Their code is mostly still present but **dormant**; don't re-wire it.

**All user-facing UI text MUST be in English — permanent user rule (2026-07-05), no exceptions, applies to every future change.** Code comments are in Indonesian.

**Two game modes** picked on the `#modeSelect` screen at load (plus an EASY/NORMAL/HARD difficulty row — `applyDifficulty` recomputes CFG from the pristine `CFG_BASE`, per-difficulty high scores):

- **Survival** — round-based waves defending the Monas monument; robots prioritize the Monument over the player; clearing a wave opens the Field Shop. Score = shop currency. Opens with a **9-shot in-engine cinematic** in the park (`survival/cutscenes/monasIntro.js` — replaced the old DOM slideshow on 2026-07-27; its four story beats are a smoke-tested contract). → [docs/survival.md](docs/survival.md)
- **Campaign** — a linear 4-stage mode (intro helicopter cutscene → three abandoned-office floors → an outdoor highway/alun-alun finale with a tank boss), with a shop scene between stages. Hacking a computer (the Stage 1 mainframe, the five Stage 3 terminals) opens the **ICE BREACH circuit puzzle** — a modal scene, not a progress bar (2026-07-28). Kills drop **loot** that stays where it falls (the player must walk over it) and becomes the shop currency. → [docs/campaign.md](docs/campaign.md)

## Architecture (refactored 2026-07-05 into ES modules)

The old single-file `index.html` was split into **ES modules under `src/`** with a **scene system**. There is still **no build step, no npm dependencies, no framework** — plain static files; Three.js r128 + post-processing examples come from CDN `<script>` tags as the global `THREE` (modules do NOT import it). `package.json` is metadata-only (`"type": "module"` for Node tooling).

**→ The complete module catalog, every export, the scene interface contract, the config key table, and the how-to-add-a-stage recipe live in [MODULES.md](MODULES.md). Read it before hunting through files.**

Load-bearing rules (details in MODULES.md):

- **Scenes:** `menu` (DOM-only) → `survivalIntroScene → survivalScene` or `campaign introScene → stage1Scene → stage2Scene…` (**both modes open with an in-engine cutscene scene**: a fresh campaign start plays `introScene` before Stage 1, and every Survival start plays `survivalIntroScene` before Wave 1 — dying/restarting replays neither), managed by `core/sceneManager.js` (`setScene`/`activeScene`). All mode-specific behavior (collision walls, ground height, bullet blockers, grenade bounds, robot movement AI, radar landmarks, HUD status, drop clamping, win check, restart policy) is behind `activeScene.*` hooks — **shared systems contain zero mode if-else**. Scene files are split by role — `src/scenes/campaign/{stages,cutscenes,utility}/` and `src/scenes/survival/{,cutscenes/}` — so adding a campaign stage = one new file in `src/scenes/campaign/stages/` + wiring per the MODULES.md recipe.
- **The campaign stage worlds coexist in one THREE.Scene** far apart (stages 1–3 are indoor buildings at x≈30000 / 60000 / 90000; stage 4 is an outdoor parking-lot→highway→alun-alun level at x≈120000 — no shared survival park); `camera.far` 4000 + robot distance culling hide the far ones. Stage 1 & Stage 2 worlds are built ONCE at campaign start by `stage1.enter`; the **Stage 3 & Stage 4 worlds are built lazily (guarded) in their own `enter`**. Every campaign stage places its OWN robots + supplies in its OWN `enter()`. Every campaign robot carries `z.stage`; a stage transition disposes the previous stage's robots silently. Campaign restart (death) always re-enters stage 1 (arrays cleared by `resetGame` first). Stages 1–3 also wrap their building in a decor-only Jakarta cityscape ring — see [docs/campaign.md](docs/campaign.md).
- **All gameplay-tunable numbers live in `config/gameplay.json`**, loaded into `CFG` (`core/config.js`) before the game starts. Read `CFG.x.y` inside functions only (never at module top level). New tuning values go in the JSON, not as code constants. Visual-only values (FOV, animation amplitudes, colors) intentionally stay in code.
- **Cross-module state = live ESM bindings**: the owning module exports `let` + setters (`isPaused`/`score` in `core/state.js`, `stamina`/`dodgeActive`/`dodgeProgress` in `entities/player.js`, `currentWeapon`/`isAiming`/`switchAnim` in `entities/weapons.js`, `scene`/`camera`/`renderer` in `core/renderer.js`). Circular imports are fine and used (weapons↔player, robots↔effects, stage1↔stage2, game↔input) **as long as bindings are only used inside functions**.
- **`updateGame()` block order in `core/game.js` is a contract** (matches the old `update()`): scene updateMode → weapon timers → player movement → weapon state → shooting → grenades → explosions → blood → drops → bullets → robots → win check. Bullets must move before the robot sweep hit-test.
- **The `camera` is a LOGIC PIVOT, not the renderer** (top-down pivot 2026-07-11). Its position = the player's eye-height point and its yaw = the aim direction toward the cursor; every gameplay system (robot targeting, bullet/melee direction, pickups, scene collision, radar, spawn points) reads it and is unchanged from the FPS era. Rendering is done by **`viewCam`** (renderer.js) at a fixed oblique offset `CAM_OFF`, overridable per-scene via `camOffset`. Because the camera looks from the southwest, **screen-up ≠ −z**: the exported ground-plane basis `SCREEN_UP`/`SCREEN_LEFT` is what keeps WASD and the radar screen-relative — never hardcode W=−z/A=−x. Full detail (dead-zone follow, `camBounds`, the avatar rig) → [docs/presentation.md](docs/presentation.md).
- **Frame order in `animate()`:** `updateTopdownAim` → `updateGame` → `followViewCam` + `updatePlayerAvatar` → decor → render. Decor animation runs every frame **even while paused**. **There is exactly ONE global time scale: `globalTimeScale()`** (`core/timeScale.js`) — `animate` computes `dt = dtReal × globalTimeScale()` and passes BOTH (`updateGame(dt, step, T, dtReal)`). It multiplies the two sources that exist (death slow-motion from `deathCine.js`, melee **HIT-STOP** from `addHitStop`) and returns **exactly 1** when neither is active, so normal frames are unchanged. Anything that must ignore slowdown (the death director, the GAME OVER countdown, `Date.now()` fire rates) uses `dtReal`. **A new slowdown source becomes a factor inside `globalTimeScale()` — never a second multiplier in the render loop.**

## Key mechanics and conventions

- **Collisions are distance checks, not physics.** Robot-hit, pickup, and blast use `distanceTo` radii. **Bullet-vs-robot is a swept-segment check** (`segPointDist2`, prev→current position; spawn-frame segment starts at the player's EYE so point-blank never tunnels). Survival: Monas is a solid AABB resolved PER-AXIS (`resolveMonas` in world.js — `MONAS_HALF` 22, base 44×44; hug-and-slide, NOT a full revert, so the player never sticks — mirrors the campaign wall fix), solid trees/fountain cylinders (`resolveObstacles`), fence clamp. **`bulletBlocked` follows the real Monas silhouette height-by-height** (base 44 low → thin obelisk ~16 at eye height, nothing above y 64) so bullets pass through the empty air beside the obelisk and hit robots behind — do NOT revert it to a flat 44-wide column. Campaign: walkable-union tests (`stage1Walk` grid / `highwayWalk`) with per-axis `slideWalk` (hug walls, don't stick) + rotated-AABB `resolveBlockers` (medians/wrecks/furniture; standable tops are walkable). Robot bodies are solid to the player only (push-out at `CFG.robot.bodyBlockRadius` 7.5, deliberately < claw-stop 8.0 so an attacking robot doesn't shove the player every frame). **Robots also collide with EACH OTHER** (`separateRobots()` in robots.js, run once per frame at the end of `updateRobots` after all movement): any two robots closer than the sum of their separation radii (`CFG.robot.separationRadius` 4.0 × scale — **kept ≤ half a grid cell's usable width so two robots still fit through a 1-cell corridor**) are pushed apart along the connecting line by `CFG.robot.separationRelax` (0.5) × overlap — a soft, converging push (no jitter), NOT a hard snap; `'idle'` (dormant campaign) robots are ANCHORS (they push others but don't move), `'jumping'` (fence vault) robots are skipped. This stops robots stacking on one point; when the player is surrounded, the ones that can't fit the front ring get pushed outward and WAIT behind it. Each pushed robot is then re-clamped to walkable space via the **`activeScene.clampRobot(z, oldX, oldZ)`** hook — without it the push shoves robots THROUGH walls, because each scene's per-frame wall-resolve reverts to the frame's start position, which was already inside the wall; `separateRobots` snapshots each robot's valid pre-separation position and passes it as the hug-slide fallback. Implementations: survival = fence + `resolveMonas` + `resolveObstacles`; campaign = `campaignClampRobot` (`stage.resolve` furniture + per-axis `stage.walkable` slide, shared in common.js).
- **Frame-rate independence:** `dt` (clamped 0.05) and `step = dt*60`. Multiply motion by `step`; decrement timers by `dt`. Fire-rate/reload use real `Date.now()` time.
- **Entity model:** six arrays in `core/state.js` — `bullets, enemyBullets, robots, grenades, explosions, drops` — iterated backwards for splicing. `enemyBullets` = robot ranged fire → player. `explosions` doubles as a generic visual-decay pool (ground puffs ride it). Drops carry a `type`: `'ammo'` (+ a `weapon` key — **ammo is PER-WEAPON since 2026-07-26**, four distinct meshes in `entities/ammoPickups.js`; picking one up fills only that weapon, and ammo for an unowned weapon is left on the floor), `'medkit'`, or `'loot'` (campaign money). Destructible **supply crates** (`entities/crates.js`) and **explosive barrels** (`entities/barrels.js`) live in their own arrays, are solid to the PLAYER ONLY and are deliberately NOT baked into nav. "Blood" (GREEN COOLANT — robots bleed coolant; `Blood*` function names kept) is a **fixed pool of 72 sprites**, each with a velocity so it SPRAYS + falls — `spawnBloodBurst(x, y, z, dirx, dirz, n, power, spread)`, where `spread` = cone width (`6.283` = 360°, used by explosions); explosion flashes a **fixed pool of 3 lights** — **keep point-light counts constant (no mid-game shader recompiles)**. New entity type = mesh + array + update block + `resetGame` cleanup.
- **Coordinates are large-scale**: 1 m ≈ 7 units (`CAMP_M`); eye height 11.4; park half-extents 620×340; keep new geometry proportional.
- **`resetGame()`** (core/game.js) clears every entity array (incl. `enemyBullets`) + pools (+ `resetRobotsFx()` launcher-boom queue + `resetStats()`), resets player/weapons/stamina/shop-upgrades via module reset fns, then re-enters the restart scene (`activeScene.restartScene()` — campaign always stage 1). Keep it in sync when adding entity types.

## Invariants — deliberate choices, do not "clean up"

Each of these was a specific user decision; reverting one is a regression. Detail in the linked doc.

- **No mid-game shader recompiles.** Fixed pools (gibs 64, decals 44, blood 72, 3 explosion lights), Lambert/Basic materials, and `core/preload.js` `warmupAll()` exist to prevent hitches. New lazily-revealed meshes or first-use materials MUST be added to the warm-up list. Don't call `applyQuality` mid-game. **PointLight counts are constant WITHIN a stage but differ BETWEEN stages** (revised 2026-07-26): the four campaign worlds share one scene, so all 54 room/street lamps used to be shaded on every fragment (57 point lights) — now only the active stage's lamps are `visible` (`registerStageLight`/`setActiveStageLights` in world/lighting.js, keyed by each scene's `lightsKey`, switched by `setScene`), which is 15-21 instead of 57. The count only changes at a stage switch, and `precompileStageLightSets(scene)` — called once at the end of `stage1.ensureWorld` while the loading screen is still up — compiles the program for EVERY light configuration up front, so the transition itself still has no recompile hitch. **Never register a global light** (explosion pool, muzzle flash) with `registerStageLight`; those must stay lit in every stage.
- **Big ground surfaces are Lambert, not Phong.** Stage 4's base/parking/paving/grass/sidewalk/verge/wheel-stop materials were Phong with a near-black `specular` (0x0c0b09-0x141310) — invisible highlights that still cost a specular term per light per fragment, on the surfaces that fill most of the screen. Only the road and alun-alun ring stay Phong (they need `normalMap`, which r128 Lambert lacks) plus the lamp poles (real metal sheen). Same reasoning as the older "interior floors are MATTE Lambert" rule.
- **Campaign decor is MERGED, not added prop-by-prop** (`utils/meshBatch.js`, 2026-07-26). Two entry points: `addMergedStatic(parent, objects)` welds many props into one mesh per material appearance (stages 1-4 collect into a local `staticProps` array and flush at the end of `buildWorld` — 12 / 14 / 14 objects for the indoor floors), and `mergeObjectInPlace(obj)` welds WITHIN one object, keeping its transform and its own material instances — that one is required for stage 4's cars and roadside buildings, whose materials `registerOccluder` fades at runtime. **`classifyForBatch` decides each child's fate: LineSegments (the crate's amber edge), PointLights (street lamps — dropping one changes the light count and forces a shader recompile), sprites, InstancedMeshes and transparent glass are PRESERVED, never welded away.** Only static opaque geometry merges; anything that moves, toggles `visible` or changes colour (sliding doors, shrouds, EXIT signs, markers, spawn machines, blast door, crates, barrels) stays a standalone object. `blockers`/nav come from the tables, so batching cannot affect collision or pathing.
- **`#crosshair` stays permanently hidden via CSS**, with all JS writes intact so shooting/recoil stay byte-identical. Don't re-show it, don't delete the writes.
- **The radar has no gradient background and no rotating sweep** (removed by user request) — don't re-add. It is SCREEN-aligned via `SCREEN_UP`, not north-locked.
- **The pause menu has no "click anywhere to resume"** — `#pauseResume` is the only resume path. Don't re-add the hint.
- **The helicopter is deliberately over the 25-mesh prop cap** (hero cutscene asset; smoke uses `MESH_CAP.Helicopter` 70). Don't simplify it to fit.
- **Interior floors are MATTE Lambert** — no specular, no normalMap. The earlier Phong floor glared under the lamps.
- **`avatarGunTip` sits at its exact calibrated offset** (the bullet spawn point + muzzle-flash parent). Don't move it; the Lv3 launcher `TIPS` override is the one deliberate exception.
- **Bullet floor-hit FX spawn at the bullet's actual clamped end position**, not the frozen cursor point — the old behavior pinned every shot to one spot and hid the spread.
- **Indoor grids have NO double walls** — exactly 1 wall cell between adjacent rooms. Smoke test 16b enforces it (0 bands for all three stages).
- **Robots take no visible damage feedback** by design — the player must not be able to read a robot's remaining HP.
- **Barrels and supply crates are solid to the player only and stay OUT of the nav grid.** Destroying one must never require a nav rebake, and a robot must never get trapped behind one. Furniture is the opposite: it goes into `blockers` and IS baked into nav (solid to player and robots alike).
- **Mission text names no compass directions** (2026-07-26, user request) — no "south", "far-right room", etc. The player finds objectives themselves; the smoke suite sweeps every campaign `showStageMsg`/`showPickup`/`hudStatus` string.
- **Dormant-but-kept systems:** reload/magazines, ADS, crouch, jump, sprint, the thrown grenade, and the medkit hold-to-channel. The code is still there and must stay unreachable.

## Editing guidance

- **ART STYLE = "GIBS 2045"** (single source of truth: [src/world/palette.js](src/world/palette.js)) — theme "Jakarta 2045, mildly futuristic, NOT cyberpunk". Rules: (1) warm dusty base materials (`PAL.gunmetal/ink/steel/panel/concrete` — no pure black, no cold blue-black); (2) ONE civic-tech accent, faded TEAL `PAL.tech` (all screens/strips/touchpads) — pure cyan `0x00ffff`, magenta `0xff00ff`, and neon underglow are BANNED (`FORBIDDEN_HEX`); (3) human/player accent = AMBER `PAL.amber` (matches the HUD) + sparse red-white `PAL.hazard`/`PAL.white`; (4) environment emissiveIntensity ≤ `EMISSIVE_MAX` 0.9 (combat FX exempt); (5) gameplay signal colors are reserved (robot eye red, class armor C/B/A, coolant green, player blood red, enemy plasma blue, EXIT green) — never use them for decor. All 14 `futuristic*` props, both stage-4 car palettes, and the boss tank paint follow it; **the smoke suite enforces the no-neon + emissive-cap rules by material sweep** — new visual assets MUST use PAL tokens.
- Keep the project a **static, buildless site**: no bundlers, frameworks, or npm dependencies (package.json stays metadata-only). It must run from a plain HTTP server.
- Follow the architecture rules at the top of [MODULES.md](MODULES.md) (scene hooks instead of mode if-else; CFG for tunables; live-binding state ownership; updateGame block order) and update MODULES.md whenever modules/exports/config keys change.
- Preserve the controls and core mechanics listed in the Overview unless the user asks for gameplay changes.
- If you edit an indoor room layout, re-verify grid connectivity (BFS over floor cells from the stage's start cell) and that no furniture blocker parks in front of a doorway.
- When you add a mechanic, put its prose in the matching `docs/` file and leave at most a one-line pointer here — this file is loaded into every session, so it stays lean.
