**Occlusion fade: ONE shared system, 20% opacity, HALF-BODY threshold, walls included (2026-08-13/14, three user requests):** `campaign/utility/occlusion.js` owns every occluder in Stages 1-13 and `CFG.campaign.occlusion.opacity` (0.2) is the only fade value — it replaced THREE divergent copies (Stage 4's line-of-sight test at 0.45, Stage 11/13's plain distance-to-player tests at 0.18/0.42 which ignored robots entirely) and filled the gap in Stages 5-10 & 12, which had nothing. Six rules. (1) **A prop fades only when it hides at least `coverFraction` (0.5) of the character's height** — the entity→camera ray is intersected with the prop's footprint (2-D slab test) and `cover = (top − feetY) − slope · tEnter` must clear `bodyHeight × coverFraction`; things that only cover the legs stay opaque. Use the SLAB test, never "distance to centre minus half-extent": a long vehicle occludes from its rear face, and a large HOLLOW building (Stage 10's 180-unit warehouse shell) must not count for someone standing 100 units to the side. `slope` comes from `camOffsetActive()` so a stage with its own `camOffset` (3/7/8) needs no copy of the constant, `bodyHeight` derives from `CFG.player.eyeHeight`, and both the player pivot AND every robot within `robotRange` are swept — that is the "or robot" half. (2) **`registerOccluder` CLONES the prop's materials**, because stage decor shares a handful of `M.*` instances and fading the shared one would fade the whole batch; clones are made at world-build time, so the no-mid-game-shader-recompile invariant holds (`transparent`/`opacity` are not in the r128 program key). (3) **A prop that must fade cannot sit in `addMergedStatic`'s batch — use `weldOccluder`** (`mergeObjectInPlace` + register): it keeps the prop's own transform and materials for a few draw calls and makes frustum culling FINER, which is why Stage 7's per-125 m vehicle batch became one welded node per vehicle for all 240 cars (the chunk binning is still computed and reported; never make it one route-wide batch). Moving props (the port crane's carried containers) register with `dynamic:true`. (4) **WALLS fade too, via `campaign/utility/wallFade.js`** — a `#` cell is never faded, it is SWAPPED: hidden from its InstancedMesh (matrix scaled to zero) and replaced by a pooled proxy carrying its own cloned materials, so each cell eases on its own curve. The `buildDetailedWallCell` skin is instanced per (face × material) so it disappears with its cell; fixed cost is ≤ 17 draw groups per stage (1 body + ≤ 16 skin), smoke-guarded. (5) **Re-identify the show/hide matrix** — `setPosition` only writes translation, so reusing the matrix that just zero-scaled a cell brings it back at scale 0 and the wall is gone for good (`placeMatrix()` calls `identity()`; the smoke `Matrix4`/`InstancedMesh` stubs record scale so this is mutation-tested). (6) **Stage 8 registers none on purpose** — all its scenery sits beyond |z| 96 while the player is locked to |z| ≲ 44, so nothing static ever enters the sight corridor. → [docs/campaign.md](docs/campaign.md#occlusion-fade--one-system-one-number-stages-113-2026-08-13-user-request)

**Every gunship projectile is born at its MUZZLE (2026-08-18, user request "buat agar peluru gunship benar-benar keluar dari moncong senjatanya, bukan tiba-tiba spawn di tengah jalan"):** the anchors had existed on the rig since it was built — `mgMuzzle`/`cannonMuzzle` on the FRONT chin turret and the new `missileRails` on the left/right wing pods — but all three fire functions ignored them and used invented offsets near the asphalt (y 8-13) already sitting in the TARGET lane, so every shot appeared out of thin air in front of the player. Now `getWorldPosition` supplies each spawn (the `tank.js` pattern, one module-level scratch vector, no allocation per shot) and the projectile flies from there to its aim point. Three consequences that must hold. (1) **The MG corridor still means something**: fire converges on the target lane at the PLAYER's x, so the lateral offset is largest at the muzzle and zero where the player actually stands — it never rakes a neighbouring lane where anyone is standing. (2) **The cannon keeps its exact timing**: the shell's velocity is scaled so its X component stays exactly `cannonSpeed`, so moving the spawn cannot silently change the dodge window (the nose muzzle is ~22 units nearer the player than the old spawn, which is the only intended change). (3) **The missile dives**: it launches at wing height and eases to `MISSILE_CRUISE_Y`, because homing steers in XZ only and a missile left at wing height would fly over the player's head while still registering a hit. **The GRD LTV-45's FRONT AXLE steers (2026-08-19, user request "ketika berbelok, buat agar ban depan GRD LTV-45 juga berbelok dong"):** the wheels already bake their axle into the GEOMETRY (`geo.rotateX(π/2)`), which leaves `rotation.z` for rolling and — this is the payoff — `rotation.y` free for steering; Euler XYZ composes them as Ry·Rz, i.e. the wheel spins on its own axle first and the whole assembly is then yawed, which is exactly a steered wheel. **The angle is derived, not authored**: the vehicle runs forward at `roadSpeed` while sliding sideways at `steerVel`, so its true heading is `atan2(lateral, forward)` and that is where the front wheels point (~0.38 rad at full lateral speed). Two things that are easy to get wrong and are smoke-guarded: **the body yaw is SUBTRACTED** (the wheels are children of a group that is already yawed, so steering would otherwise count twice), and **the hubs steer with their tyres** or the rim stays straight inside a turned tyre. The mechanical limit (`STEER_MAX`) and the steering lag live in the VEHICLE module, because how far a wheel can turn is a property of the vehicle; only the kinematics live in the scene. **A pivot carried by a vehicle is never a walk cycle, and a swerve THROWS the rider (2026-08-19, user request "ketika berbelok, major gibran tidak menampilkan animasi jalan. tampilkan animasi seperti terhempas. tau kan? aksi reaksi newton"):** Stage 8 now calls **`setAvatarCarried(true)`** for the whole ride — the same rule Stage 5's train established, and free steering is what made it bite here, because the avatar's gait is derived from PIVOT DISPLACEMENT and steering moves the pivot sideways. On top of it, **`setAvatarVehicleLean(normalisedLateralAccel)`** rolls and shifts the whole avatar OPPOSITE the vehicle's acceleration, on a lightly overshooting spring so it reads as a lurch. **It is fed ACCELERATION, never velocity** — that is the whole point of the request: holding a steady sideways speed lets the body settle upright again, and it is starting and stopping the swerve that throws him. **Its amplitude is CAGED BY THE HATCH (2026-08-19, follow-up "terhempasnya terlalu berlebihan ... agar major gibran masih tetap berada di area lubang di atas mobil"):** the tilt/shift constants were cut to 0.15 rad / 0.9 units (from 0.42 / 2.6), but the real guarantee is `setAvatarVehicleLeanCage(halfWidth)` — the scene passes the roof hatch's own opening half-width (`vehicle.hatchHalfZ`, derived from the leaf geometry and slide, not a literal) and the shift is clamped to a fraction of it, so no future retune of the feel constants can throw the gunner out of the hole he is standing in. Measured peak: 0.79 units of shift against a 3.29-unit half-opening, 0.13 rad of tilt. The tilt goes on `avatarGroup.rotation.x` and is applied LAST in the frame, so it rides on top of whatever pose was chosen (idle, firing, dying) instead of being overwritten, and Euler XYZ keeps Rx outermost so the axis stays the world travel axis no matter which way he is aiming. Manning a vehicle also now blocks the AFK idle poses — with the gait pinned at zero, a gunner with a still cursor would otherwise wave and then lie down on the roof hatch. **Stage 8 steers FREELY — the A/D lane snap is gone (2026-08-19, user request "coba buat agar mobil player tidak snap ke kiri dan ke kanan dong. coba bikin lebih fleksibel"):** holding A/D accelerates the GRD LTV-45 sideways and it stops wherever it is released, anywhere across the carriageway. **The change is cheap because `currentZ` became the source of truth and `laneIndex` became a READ-OUT of it** (`nearestLane`) — every system that asks "which lane is the player in" (the gunship telegraph, the hauler's lane chase, barrel snapping) keeps working untouched, and projectiles still commit to lane CENTRES so the telegraphs stay readable. Four things are derived rather than invented: peak lateral speed is `laneWidth / laneChangeSec` (one lane still costs what it always did), the median still slows you by the existing `laneChangeSec : medianChangeSec` ratio, `steerEaseSec` is the only new key (the accel/damping that makes it analog instead of a teleport), and the vehicle yaws toward its steer direction — visual only. **A consequence worth keeping:** clipping one lane over is no longer enough to dodge a barrel, because stopping on the lane boundary still leaves you inside its width — you now have to actually clear it. Never reintroduce a snap-to-centre pull on release; smoke fails on any drift after the key comes up. **Stage 8 also DRIVES FORWARD AND BACK (2026-08-20, user request "selain mobil player bisa belok kiri kanan, mobil player bisa bergerak ke depan dan ke belakang"):** `W`/`S` move the LTV-45 up and down the road inside `advanceRange` (96) of the arena centre, held-not-edge-triggered and stopping wherever released, on its own `advanceEaseSec` because a vehicle changes longitudinal speed far more lazily than it slides sideways. **`PLAYER_X` is demoted from "where the player is" to "the CENTRE of the arena" and `currentX` becomes the source of truth** — the same inversion `currentZ` got the day before. That splits a distinction which was invisible while the player was pinned, and getting it backwards is not subtle: **things that CHASE the player (hauler station/lane lock, carrier combat offsets, gunship `roadX`/`bossX`, loot + `clampDropPos`, cutscene framing) read the LIVE `currentX`, while things that are part of the WORLD (the fixed road pool's ends, `stage8Walk`'s arena bounds, `S8_START`) stay anchored to the CENTRE.** Entry positions must satisfy BOTH at once — outside the road pool AND outside the player's view — so the ctx field is now the absolute `roadMaxX` rather than a relative `roadEdge`; pointing the pool end at the live player spawned carriers past the end of the asphalt the moment the player drove forward (smoke caught it). Two derived numbers: peak drive speed is **CLAMPED below `roadSpeed`** (`ADVANCE_SPEED_CAP` 0.9) because a player falling back faster than the asphalt scrolls would need the wheels spinning BACKWARDS while the landscape still swept rearwards — braking must never become reversing (measured 92 → 48.6) — and the wheels roll at **`groundSpeed()` = `roadSpeed + advanceVel`**, not the scroll rate, which is also what the front-wheel steer angle is derived from. Stage 5 C2 and each of the three Stage 6 generators pass `ADVANCED_REPAIR_PARTS` to `repairScene`: exactly PHASE SYNC then ROTOR KICKSTART, with completed-board progress surviving abort. **PHASE SYNC (2026-08-19, user request) is the first generator board, and it is the FOURTH design in that slot on the same day — the three it replaced each teach a rule.** (1) **FUSE LOADOUT: a board played four times per run must GENERATE its answer** — its solution was the constant `FUSE_AMPS.slice(2, 2+n)`, so three of the four playthroughs were pure recall. (2) **START INTERLOCK: a board whose optimal play is BRUTE FORCE has no tension** — it generated its answer correctly, but every requirement was printed on the breaker card and a wrong close was free, so clicking every row repeatedly was the *fastest* strategy. (3) **FAULT ISOLATION ("terlalu rumit"): this is a generator repair in the middle of a combat stage, not a logic puzzle — it must be understood by LOOKING at it.** Tree, meter, probes and PAR all had to be read and held in the head. So Phase Sync has **no hidden information and nothing to read**: an oscilloscope draws a bright bus reference plus one trace per phase, with a slider under each; slide each trim until the traces collapse into one steady line, every lamp turns green and the turbine spools up. **Its ONLY difficulty is COUPLING** — moving one slider drags the others a fraction of the same distance (`syncCoupling`), exactly as real machines load each other, so one pass down the panel never finishes it and the player comes back to trim again (measured: every board converges within **two sweeps**). Four rules. (a) **Everything derives from ONE quantity, `syncError(g,i)`** — Hz readout, amplitude readout, lamp colour and the trace's own frequency/amplitude/phase — so the panel cannot disagree with the model, and landing on the mark reads exactly 50.0 Hz at 100%. (b) **Always solvable, PROVEN not hoped**: setting each slider exactly and moving on is Gauss-Seidel on a unit-diagonal matrix, which converges iff `(n−1)·|c| < 1`, and **`syncCoupling(n)` clamps the configured value to 0.9 of that bound** so no retune the user types can make a board unsolvable; targets are also kept away from both ends of the track so coupling can never push an answer out of a slider's range. (c) **No countdown, no way to lose** (2026-07-29 rule) — a bad slide is slid back. (d) **The scrolling waves are purely visual**: they roll on the modal's own `setInterval` (the game loop is paused, the same reason ICE BREACH owns its countdown), the tick touches no gameplay value so a board can never solve itself while watched, and `paintSync` repaints only the scope markup plus kept slider references — never a full `renderBoard`, which would rip the slider out from under the cursor mid-drag (the `paintRotor` lesson). Track-click and drag are both live, the same pairing the wire/chip boards have had since 2026-07-29, and the win layers the existing turbine asset over the success tone rather than adding audio for one board. Kickstart requires clockwise flywheel motion, green-band ignition, then the master breaker; a mistimed ignition only costs RPM. **The flywheel BLEEDS RPM (`rotorDecayPerSec`, 2026-08-19), and that is what makes the green band a WINDOW rather than a counter** — without decay, RPM only ever rose, so "fire ignition inside the green band" promised timing the board did not have and the whole thing was `crank ×N → ignition → breaker`. Two tuning invariants, both smoke-asserted from `CFG`: one CRANK click must move RPM LESS than the band is wide (or the button-only path could step over the band and never land in it), and `bandWidth / rotorDecayPerSec` must stay a human window (currently 2.0 s). The Stage 6 HQ upload remains its scripted story cutscene. Signal Trace time counts toward `stageStats` like the other modal puzzles. Tuning lives in `campaign.signalTrace`, `campaign.repair.advanced`, and Stage 6's `signalCooldownSec`/`encounters.signalAlarm`.

## Architecture (refactored 2026-07-05 into ES modules)

The old single-file `index.html` was split into **ES modules under `src/`** with a **scene system**. There is still **no build step, no npm dependencies, no framework** — plain static files; Three.js r128 + post-processing examples come from CDN `<script>` tags as the global `THREE` (modules do NOT import it). `package.json` is metadata-only (`"type": "module"` for Node tooling).

**→ The complete module catalog, every export, the scene interface contract, the config key table, and the how-to-add-a-stage recipe live in [MODULES.md](docs/MODULES.md). Read it before hunting through files.**

**`src/utils/` is the shared layer every scene and entity leans on** — reach for it before writing a new helper: `pathfind.js` (nav grid + grid-LOS + A* + `navAim`/`turnToward` — all robot chasing), `collision.js` (`slideWalk`/`resolveBlockers`/`blockersGroundHeight`/`resolveCylinders` — the hug-and-slide primitives), `meshBatch.js` (static decor welding), `textures.js` (procedural canvas textures + normal maps), `sfx.js` (every sound + the three music tracks + volume state), `math.js` (`rand`/`clamp`/`smooth`/`segPointDist`).

Load-bearing rules (details in MODULES.md):

- **Scenes:** `menu` (DOM-only) → `survivalIntroScene → survivalScene` or `campaign introScene → stage1Scene → stage2Scene…` (**both modes open with an in-engine cutscene scene**: a fresh campaign start plays `introScene` before Stage 1, and every Survival start plays `survivalIntroScene` before Wave 1 — dying/restarting replays neither), managed by `core/sceneManager.js` (`setScene`/`activeScene`). A fresh campaign start also plays the **story PROLOGUE** (`prologueScene` in `cutscenes/prologue.js`) BEFORE the heli intro: main.js sets `introScene` first (worlds built, heli armed + warmed), then swaps in `prologueScene`, which hands back with **`resumeScene(introScene)`** — resume, NOT `setScene`, so `introScene.enter()` never runs twice; details in [docs/campaign.md](docs/campaign.md). All mode-specific behavior (collision walls, ground height, bullet blockers, grenade bounds, robot movement AI, radar landmarks, HUD status, drop clamping, win check, restart policy) is behind `activeScene.*` hooks — **shared systems contain zero mode if-else**. Scene files are split by role — `src/scenes/campaign/{stages,cutscenes,utility}/` and `src/scenes/survival/{,cutscenes/}` — so adding a campaign stage = one new file in `src/scenes/campaign/stages/` + wiring per the MODULES.md recipe.
- **The campaign stage worlds coexist in one THREE.Scene** far apart (stages 1–3 at x≈30000 / 60000 / 90000; stage 4 at x≈120000; stage 5 at x≈180000; stage 6 at x≈210000; stage 7 at x≈240000; stage 8 at x≈270000; then Kertajati x≈300000, port x≈330000, forest x≈360000, IKN surface/root x≈390000/400000, and Monas x≈430000 — no shared survival park); `camera.far` 4000 + root visibility + robot distance culling hide the far ones. **ALL THIRTEEN worlds are built ONCE up front by `stage1.ensureWorld()`**, then `prewarmCampaignWorldRoots()` temporarily reveals each registered root/light/phase viewpoint before `precompileStageLightSets()`. Each later stage retains a guarded fallback builder. Every campaign stage places its OWN robots + supplies in its OWN `enter()`, and each robot carries `z.stage`. Death reloads the saved active checkpoint; Pause → Restart Game deliberately returns to Stage 1. Stages 1–3 alone use the generic Jakarta cityscape ring; Stages 9–13 own theme-specific procedural worlds. See [docs/campaign.md](docs/campaign.md).
- **All gameplay-tunable numbers live in `config/gameplay.json`**, loaded into `CFG` (`core/config.js`) before the game starts. Read `CFG.x.y` inside functions only (never at module top level). New tuning values go in the JSON, not as code constants. Visual-only values (FOV, animation amplitudes, colors) intentionally stay in code.
- **Cross-module state = live ESM bindings**: the owning module exports `let` + setters (`isPaused`/`score` in `core/state.js`, `stamina`/`dodgeActive`/`dodgeProgress` in `entities/player.js`, `currentWeapon`/`isAiming`/`switchAnim` in `entities/weapons.js`, `scene`/`camera`/`renderer` in `core/renderer.js`). Circular imports are fine and used (weapons↔player, robots↔effects, stage1↔stage2, game↔input) **as long as bindings are only used inside functions**.
- **`updateGame()` block order in `core/game.js` is a contract** (matches the old `update()`): scene updateMode → weapon timers → player movement → weapon state → shooting → grenades → explosions → blood → drops → bullets → robots → win check. Bullets must move before the robot sweep hit-test.
- **The `camera` is a LOGIC PIVOT, not the renderer** (top-down pivot 2026-07-11). Its position = the player's eye-height point and its yaw = the aim direction toward the cursor; every gameplay system (robot targeting, bullet/melee direction, pickups, scene collision, radar, spawn points) reads it and is unchanged from the FPS era. Rendering is done by **`viewCam`** (renderer.js) at a fixed oblique offset `CAM_OFF`, overridable per-scene via `camOffset`. Because the camera looks from the southwest, **screen-up ≠ −z**: the exported ground-plane basis `SCREEN_UP`/`SCREEN_LEFT` is what keeps WASD and the radar screen-relative — never hardcode W=−z/A=−x. Full detail (dead-zone follow, `camBounds`, the avatar rig) → [docs/presentation.md](docs/presentation.md).
- **Frame order in `animate()`:** `updateTopdownAim` → `updateGame` → `followViewCam` + `updatePlayerAvatar` → decor → render. Decor animation runs every frame **even while paused**. **There is exactly ONE global time scale: `globalTimeScale()`** (`core/timeScale.js`) — `animate` computes `dt = dtReal × globalTimeScale()` and passes BOTH (`updateGame(dt, step, T, dtReal)`). It multiplies the two sources that exist (death slow-motion from `deathCine.js`, melee **HIT-STOP** from `addHitStop`) and returns **exactly 1** when neither is active, so normal frames are unchanged. Anything that must ignore slowdown (the death director, the GAME OVER countdown, `Date.now()` fire rates) uses `dtReal`. **A new slowdown source becomes a factor inside `globalTimeScale()` — never a second multiplier in the render loop.**
