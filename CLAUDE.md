# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- **Serve:** `python -m http.server 8000` (then open http://localhost:8000) — an HTTP server is MANDATORY; `file://` breaks ES modules + the config `fetch`. Internet required for the Three.js r128 CDN scripts.
- **Test:** `node tools/smoke.mjs` — headless smoke suite (zero deps, stubbed THREE/DOM driving the real `src/` modules), ~5900 lines and 750+ asserts (as of 2026-07-31). If `node` is not on PATH (non-login shells), use the VS Code server binary: `~/.vscode-server/bin/<hash>/node`. It prints `<n> pass, <m> fail`; the count grows every session, so **never assert on the total**. Sections are numbered `// --- 12b. NAME ---` comments (a few older ones use `// === NAME ===`), often wrapping a `{ … }` scope block to keep locals out of the shared top-level namespace; each assert is `T(name, ok)` ([smoke.mjs:204](tools/smoke.mjs#L204)). The `[postfx] … CDN tidak termuat` line it prints is expected (no network in Node), not a failure. There is **no per-test filter** — it's a flat sequential script, so run the whole file (comment out sections to isolate one). The `localStorage` stub is a real in-memory Map, so save/checkpoint is testable. Coverage list at the end of docs/MODULES.md.
- **Lint:** `node --check src/<file>.js` — per touched file (`"type": "module"` makes this work).
- **Mandatory per gameplay change:** add/adjust smoke asserts → `node tools/smoke.mjs` until green → `node --check` every touched file → sync CLAUDE.md + docs/MODULES.md.
  - Keep asserts **CONFIG-DRIVEN** (read `CFG`, never hardcode tuned numbers). The user hand-tunes `config/gameplay.json` between sessions; a test failing right after a pure config retune almost always means the test hardcoded a number.
  - A missing stub method (fakeEl/THREE) is a harness gap, not a game bug — extend the stub.

## Overview

Browser **TOP-DOWN SHOOTER** (Alien Shooter-style; **pivoted from FPS on 2026-07-11** — see the "camera is a logic pivot" rule below): "Gibran vs Robot 3D", Three.js r128.

**Controls: WASD = screen-axis movement, mouse = virtual aim cursor (bullets follow it), LMB = shoot/use, RMB = move-to-cursor-point (WASD cancels), 1/2/3 = the three weapon slots, Q cycles weapons, 4 = use a medkit instantly, F melee, Shift dodge/evade (brief-invincible **combat roll** — animation rewritten 2026-07-27, see docs/presentation.md). Crouch, jump, ADS, sprint (replaced by the dodge), R/reload (magazine system removed) and the thrown grenade (replaced by the Grenade Launcher weapon) do not exist** — all removed in the 2026-07-11 pivot. Their code is mostly still present but **dormant**; don't re-wire it.

**All user-facing UI text MUST be in English — permanent user rule (2026-07-05), no exceptions, applies to every future change.** Code comments are in Indonesian.

**All spoken dialogue shown in a dialogue box MUST reveal character-by-character (typewriter), never appear fully in one frame — permanent presentation rule (2026-08-01).** Typing speed and the full-text hold must be config-driven. Speaker labels may appear immediately; narration captions and short HUD/status messages are not dialogue boxes and are exempt.

**Two game modes** picked on the `#modeSelect` screen at load (plus an EASY/NORMAL/HARD difficulty row — `applyDifficulty` recomputes CFG from the pristine `CFG_BASE`, per-difficulty high scores):

- **Survival** — round-based waves defending the Monas monument; robots prioritize the Monument over the player; clearing a wave opens the Field Shop. Score = shop currency. Opens with a **9-shot in-engine cinematic** in the park (`survival/cutscenes/monasIntro.js` — replaced the old DOM slideshow on 2026-07-27; its four story beats are a smoke-tested contract). → [docs/survival.md](docs/survival.md)
- **Campaign** — a linear 8-stage mode (a **9-era story prologue** [2028→2045, `cutscenes/prologue.js` — typed text on the left, a per-era SVG illustration on the right (`prologueArt.js`), all on a pitch-black screen since 2026-07-31; see the invariant] → intro helicopter cutscene → three abandoned-office floors → an outdoor highway/alun-alun tank battle → the depot-and-military-train journey to Bandung → Bandung Headquarters, where the valid kill-switch upload fails because only the central transmitter in IKN can broadcast it → branching Bandung streets ending at the Cisumdawu toll gate → an autonomous GARUDA firefight and combat-gunship duel en route to Kertajati), with a shop scene between stages. Hacking opens the **ICE BREACH circuit puzzle** — a modal scene, not a progress bar (2026-07-28); generator work opens **FIELD REPAIR** — three modal boards in a row, one per recovered component, with **no countdown** (2026-07-29). Kills drop **loot** that stays where it falls (the player must walk over it) and becomes the shop currency. → [docs/campaign.md](docs/campaign.md)

**ICE BREACH size/UI contract (2026-08-01):** every campaign hack uses the fixed **5×5** `CFG.campaign.hack.gridSize` board. INGRESS and DATA CORE each have a visible external trace connected to their adjacent middle-row tile; this supersedes all older `gridMin`/`gridMax` progression wording.

## Architecture (refactored 2026-07-05 into ES modules)

The old single-file `index.html` was split into **ES modules under `src/`** with a **scene system**. There is still **no build step, no npm dependencies, no framework** — plain static files; Three.js r128 + post-processing examples come from CDN `<script>` tags as the global `THREE` (modules do NOT import it). `package.json` is metadata-only (`"type": "module"` for Node tooling).

**→ The complete module catalog, every export, the scene interface contract, the config key table, and the how-to-add-a-stage recipe live in [MODULES.md](docs/MODULES.md). Read it before hunting through files.**

**`src/utils/` is the shared layer every scene and entity leans on** — reach for it before writing a new helper: `pathfind.js` (nav grid + grid-LOS + A* + `navAim`/`turnToward` — all robot chasing), `collision.js` (`slideWalk`/`resolveBlockers`/`blockersGroundHeight`/`resolveCylinders` — the hug-and-slide primitives), `meshBatch.js` (static decor welding), `textures.js` (procedural canvas textures + normal maps), `sfx.js` (every sound + the three music tracks + volume state), `math.js` (`rand`/`clamp`/`smooth`/`segPointDist`).

Load-bearing rules (details in MODULES.md):

- **Scenes:** `menu` (DOM-only) → `survivalIntroScene → survivalScene` or `campaign introScene → stage1Scene → stage2Scene…` (**both modes open with an in-engine cutscene scene**: a fresh campaign start plays `introScene` before Stage 1, and every Survival start plays `survivalIntroScene` before Wave 1 — dying/restarting replays neither), managed by `core/sceneManager.js` (`setScene`/`activeScene`). A fresh campaign start also plays the **story PROLOGUE** (`prologueScene` in `cutscenes/prologue.js`) BEFORE the heli intro: main.js sets `introScene` first (worlds built, heli armed + warmed), then swaps in `prologueScene`, which hands back with **`resumeScene(introScene)`** — resume, NOT `setScene`, so `introScene.enter()` never runs twice; details in [docs/campaign.md](docs/campaign.md). All mode-specific behavior (collision walls, ground height, bullet blockers, grenade bounds, robot movement AI, radar landmarks, HUD status, drop clamping, win check, restart policy) is behind `activeScene.*` hooks — **shared systems contain zero mode if-else**. Scene files are split by role — `src/scenes/campaign/{stages,cutscenes,utility}/` and `src/scenes/survival/{,cutscenes/}` — so adding a campaign stage = one new file in `src/scenes/campaign/stages/` + wiring per the MODULES.md recipe.
- **The campaign stage worlds coexist in one THREE.Scene** far apart (stages 1–3 are indoor buildings at x≈30000 / 60000 / 90000; stage 4 is an outdoor parking-lot→highway→alun-alun level at x≈120000; stage 5 is the depot/static train arena at x≈180000; stage 6 is Bandung Terminal→HQ at x≈210000; stage 7 is Bandung streets→Cisumdawu at x≈240000; stage 8 is the coordinate-stable Cisumdawu vehicle arena at x≈270000 — no shared survival park); `camera.far` 4000 + robot distance culling hide the far ones. **ALL EIGHT worlds are built ONCE up front by `stage1.ensureWorld()`** (guard `built`; stage 2 inline + `stage3.ensureWorld` through `stage8.ensureWorld`, then `precompileStageLightSets`) — called by `stage1.enter` and by the intro cutscene, so every shader compiles while the loading screen is still up. Stages 3–8 still call their own guarded `ensureWorld()` from `enter()` as a fallback, but they are not lazy. Every campaign stage places its OWN robots + supplies in its OWN `enter()`. Every campaign robot carries `z.stage`; a stage transition disposes the previous stage's robots silently. Campaign restart re-enters the saved stage checkpoint via the shared campaign-jump path. Stages 1–3 also wrap their building in a decor-only Jakarta cityscape ring — see [docs/campaign.md](docs/campaign.md).
- **All gameplay-tunable numbers live in `config/gameplay.json`**, loaded into `CFG` (`core/config.js`) before the game starts. Read `CFG.x.y` inside functions only (never at module top level). New tuning values go in the JSON, not as code constants. Visual-only values (FOV, animation amplitudes, colors) intentionally stay in code.
- **Cross-module state = live ESM bindings**: the owning module exports `let` + setters (`isPaused`/`score` in `core/state.js`, `stamina`/`dodgeActive`/`dodgeProgress` in `entities/player.js`, `currentWeapon`/`isAiming`/`switchAnim` in `entities/weapons.js`, `scene`/`camera`/`renderer` in `core/renderer.js`). Circular imports are fine and used (weapons↔player, robots↔effects, stage1↔stage2, game↔input) **as long as bindings are only used inside functions**.
- **`updateGame()` block order in `core/game.js` is a contract** (matches the old `update()`): scene updateMode → weapon timers → player movement → weapon state → shooting → grenades → explosions → blood → drops → bullets → robots → win check. Bullets must move before the robot sweep hit-test.
- **The `camera` is a LOGIC PIVOT, not the renderer** (top-down pivot 2026-07-11). Its position = the player's eye-height point and its yaw = the aim direction toward the cursor; every gameplay system (robot targeting, bullet/melee direction, pickups, scene collision, radar, spawn points) reads it and is unchanged from the FPS era. Rendering is done by **`viewCam`** (renderer.js) at a fixed oblique offset `CAM_OFF`, overridable per-scene via `camOffset`. Because the camera looks from the southwest, **screen-up ≠ −z**: the exported ground-plane basis `SCREEN_UP`/`SCREEN_LEFT` is what keeps WASD and the radar screen-relative — never hardcode W=−z/A=−x. Full detail (dead-zone follow, `camBounds`, the avatar rig) → [docs/presentation.md](docs/presentation.md).
- **Frame order in `animate()`:** `updateTopdownAim` → `updateGame` → `followViewCam` + `updatePlayerAvatar` → decor → render. Decor animation runs every frame **even while paused**. **There is exactly ONE global time scale: `globalTimeScale()`** (`core/timeScale.js`) — `animate` computes `dt = dtReal × globalTimeScale()` and passes BOTH (`updateGame(dt, step, T, dtReal)`). It multiplies the two sources that exist (death slow-motion from `deathCine.js`, melee **HIT-STOP** from `addHitStop`) and returns **exactly 1** when neither is active, so normal frames are unchanged. Anything that must ignore slowdown (the death director, the GAME OVER countdown, `Date.now()` fire rates) uses `dtReal`. **A new slowdown source becomes a factor inside `globalTimeScale()` — never a second multiplier in the render loop.**

New entity type = mesh + array + update block + `resetGame` cleanup.
- **Coordinates are large-scale**: 1 m ≈ 7 units (`CAMP_M`); eye height 11.4; park half-extents 620×340; keep new geometry proportional.

Keep it in sync when adding entity types.

## Invariants — deliberate choices, do not "clean up"

Each of these was a specific user decision; reverting one is a regression. Detail in the linked doc.

- **No mid-game shader recompiles.** Fixed pools (gibs 64, decals 44, blood 72, 3 explosion lights), Lambert/Basic materials, and `core/preload.js` `warmupAll()` exist to prevent hitches. New lazily-revealed meshes or first-use materials MUST be added to the warm-up list. Don't call `applyQuality` mid-game. **PointLight counts are constant WITHIN a stage but differ BETWEEN stages** (revised 2026-07-26): only the active stage's lamps are `visible` (`registerStageLight`/`setActiveStageLights` in world/lighting.js, keyed by each scene's `lightsKey`, switched by `setScene`), and `precompileStageLightSets(scene)` at the end of `stage1.ensureWorld` compiles every configuration while the loading screen is still up, so the switch itself has no hitch. **Never register a global light** (explosion pool, muzzle flash) with `registerStageLight` — those must stay lit in every stage. Counts and the reasoning → [docs/campaign.md](docs/campaign.md#2026-07-26-changes-user-request).
- **Big ground surfaces are Lambert, not Phong.** Stage 4's base/parking/paving/grass/sidewalk/verge/wheel-stop materials were Phong with a near-black `specular` (0x0c0b09-0x141310) — invisible highlights that still cost a specular term per light per fragment, on the surfaces that fill most of the screen. Only the road and alun-alun ring stay Phong (they need `normalMap`, which r128 Lambert lacks) plus the lamp poles (real metal sheen). Same reasoning as the older "interior floors are MATTE Lambert" rule.
